# Gameplay Tag 使用稳定 ID、来源计数与同步批次通知

同一 Entity 的多个 Ability 或效果可以同时提供同一标签，标签层级还需要支持父级查询；配表中的引用必须在节点重命名、移动或删除后保持身份稳定。采用独立标签框架：整数 ID 表示身份，共享 Catalog 表示层级，Entity 持有稀疏来源计数容器并通过 Token 撤销各自贡献；同步事件在完整修改提交、通过 out 交付 Token 后按批次分发。嵌套 XML 同时保存定义与单调分配的 ID，CLI 补齐并回写缺失 ID，再通过可切换的 Scriban 模板生成 C# Catalog 与 Luban 常量，使人工编辑的单一源文件维持代码和配表的一致身份。

## 备选方案

- 路径哈希作为 ID：无需保存映射，但重命名或移动会改变身份，碰撞处理也不能消除配置迁移成本。
- 独立持久 ID 映射或手工分配 ID：均可保持稳定；前者增加定义与映射的协作同步，后者将分配及防重复成本交给维护者。当前只需 XML 与 CLI，选择在定义中持久保存工具分配结果。
- 普通 Add/Remove 计数接口：调用方必须自行保证来源归属与重复移除的平衡。Token 将撤销限定到一次添加，副本重复取消不影响其他来源。
- 返回 Token 后显式触发通知：能分开添加与事件，但形成容易遗漏的两步调用契约。直接返回 Token 并在返回前通知，则同步回调无法取得该来源；out 将交付时点提前到通知前。
- 每个容器按 Catalog 分配计数数组：查询可以直接寻址，但 Entity 通常只激活少数标签，空间成本随全局标签量增长。采用标签值为键的稀疏字典，接受字典查询与容量增长的成本。
- 回调中立即递归通知或监听异常向外传播：会交错祖先通知，或让已提交修改因个别监听器异常表现为失败。使用容器 FIFO 批次与 Signal 的逐 callback 异常隔离，保留同步调用，同时避免一个监听器中断其余通知。

## 影响

ID 是配置兼容性契约：既有 ID 不重算，删除不回退 nextId，不复用已分配 ID；工具会修改源 XML，源文件的 ID 更新需要与生成结果一起评审和提交。路径改名保留身份，但路径别名与 C# 成员会随之变化，需要更新使用方。

事件参数是历史变化快照，查询读取最新已提交状态；回调可以取消或重启业务操作，调用方仍须在添加后检查自身执行身份。异常隔离不提供回滚；分发预算超限时保留状态与已交付 Token，并丢弃剩余通知。销毁采用静默 Dispose，以阻止销毁回调重新添加来源。

运行时不保留路径字符串，标签框架不依赖具体项目或 Luban；项目 Catalog 与 mapper 位于配表程序集。当前接口、生命周期与生成规则见 [Gameplay Tag 系统](../Architecture/GameplayTags.md) 和 [配表与生成代码](../Architecture/Tables.md)。
