# RuleSystem 统一处理 Condition / Action，并按条件结果变化通知

已由 [ADR-0010](0010-separate-condition-observation-and-action-dispatch.md) 取代；以下保留当时的决策背景，不作为当前接口说明。

Condition / Action 已集中到各自的总表，业务表通过稳定 ID 引用，但条件依赖索引、状态变化响应和重新求值仍分散在消费系统。决定由 Gameplay 的 RuleSystem 统一承担查表、条件解析、依赖监听、结果缓存和 Action 分发，让消费系统接收解析后的条件结果，以共享条件的求值成本并集中维护通知与热重载语义。该设计已接受，RuleSystem 尚未实现；当前有效接口仍见 [配表与生成代码](../Architecture/Tables.md)。

## 备选方案

- 各消费系统监听原始变化并自行求值：无需共享观察生命周期，但重复维护依赖索引、解析与热重载；同一个条件被多个系统使用时重复计算。
- 统一求值后在每次依赖变化时通知：可以反映底层变化，但结果不变也会触发 NPC 选择、事件检查等业务响应。选择只在布尔结果改变时发布条件结果事件。
- 扫描整张条件表或永久缓存全部结果：登记接口较少，但会持续维护没有使用者的条件；选择按消费方登记和引用计数维护观察集合。
- 由 RuleSystem 同时接管 Action 队列、完成记录与取消：会把场景或其他业务所有权带入通用分发入口；这些职责继续归调用方。

## 影响

- 消费系统在初始化时订阅条件结果事件，在入场或业务启用时按不重复的 ConditionId 登记观察；登记返回可取消的 Token 和当前结果。先建立条件到业务对象的映射，再登记，完成登记后应用初始状态；首次登记不发布变化事件。
- RuleSystem 按 ConditionId 共享依赖、缓存结果和观察者引用计数。同 ID 的多个登记各有独立 Token；取消一个登记只撤销自身贡献，副本重复取消无副作用，最后一个观察者取消后释放该条件的依赖与缓存。消费方离场或业务结束时取消登记，关闭时取消事件订阅。
- 底层状态变化只使相关、正在观察的条件重新求值。条件结果事件携带 ConditionId 和新结果，仅在 true / false 改变时发布；消费系统保留条件到自身业务对象的映射，决定 NPC 配置选择、事件触发等响应。
- 一批变化影响多个条件时，先提交全部结果缓存，再发布结果变化事件；通知中产生的新状态变化排入后续批次，避免重入求值交错更新。条件总表热重载重建观察条件的依赖并重新求值，同样遵循结果变化通知规则。
- System 负责总表与观察生命周期，具体 Resolver 接收 ConditionDef / ActionDef 并负责类型解析。Action 分发保留既有 ActionExecutionResult / IActionExecutionMonitor，调用方继续负责执行队列、完成记录与取消；行为表热重载只影响后续执行。
- 当前条件不读取调用来源，可以按 ConditionId 共享结果。本次不增加统一来源信息；今后引入依赖 NPC、事件或其他来源的条件时，必须重新定义观察身份与缓存键，不能继续只按 ConditionId 共享结果。
