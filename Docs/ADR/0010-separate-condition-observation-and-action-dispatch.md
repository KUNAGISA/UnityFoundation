# 拆分条件观察与同步行为分发，行为发起即视为成功

Condition 与 Action 已使用各自总表，但条件观察和 Action 监视仍分散在消费系统。决定由 ConditionSystem 集中共享条件依赖、缓存和结果变化通知，由 ActionSystem 集中行为分发；Action 的成功表示已发起，持续行为的生命周期和独占替换归所属系统。同步重入采用 FIFO，防止行为修改状态触发另一行为后，中断当前行为的同步逻辑。

本决定取代 [ADR-0009](0009-centralize-condition-observation-in-rule-system.md)，当前接口见 [ConditionSystem](../Architecture/Conditions.md) 和 [ActionSystem](../Architecture/Actions.md)。

后续场景事件完成记录改由业务条件表达，见 [ADR-0022](0022-condition-driven-scene-event-availability.md)；配表重载后的条件缓存改为显式刷新，见 [ADR-0023](0023-explicit-condition-configuration-refresh.md)。本记录保留当时的取舍与影响。

## 备选方案

- 单一 RuleSystem 同时提供条件观察与无状态行为分发：接口入口较少，但没有体现跨来源同步重入的协调职责；选择分开维护观察生命周期和行为执行顺序。
- 允许同步嵌套执行：无需队列，但每个 Action 都要考虑在状态修改到一半时被其他 Action 改写前提或销毁来源。
- 排队并等待持续行为完成：可以避免剧情替换，但策划约定行为发起即成功，独占冲突由所属系统取消旧行为；不引入跨帧请求和监视器。
- 出队重新检查触发条件：能跳过已经失效的事件，但会改变已触发行为的决定；本次入队锁定触发决定，只调整同步执行顺序。

## 影响

- 单次场景事件在行为成功发起后立即写入完成记录；剧情之后失败或被替换不会回滚记录或自动重试。
- 多个剧情 Action 连续发起时，后者替换前者，即使前者尚未加载完成；多个事件仍可能都已记录成功，玩法配置需符合该语义。
- 同步队列不提供状态事务，条件监听仍可能看到多次状态修改产生的中间结果。
- 条件刷新先提交本批全部结果，再发布变化通知；通知引发的按类型刷新进入 FIFO，避免缓存与通知交错。全量刷新仅由 EarlyTick 的配表重载直接发起，遵循不重入刷新的调用约定；全刷通知产生的按类型请求在本轮通知结束后继续处理。
- 调用方以可选回调接收实际执行结果，须支持回调发生在 Submit 返回前；场景消费方自行防止旧登记回调更新新场景。
- 条件观察 Token 为专用类型，不实现 ICancelToken，由消费方显式取消；条件仍按 ID 共享，不增加来源上下文。
- 常规 System 的入口信任初始化至 Shutdown 之间的生命周期契约；同步重入、失败清理和场景登记失效仍由对应所有者处理，不以重复的活动状态判断替代这些职责。
