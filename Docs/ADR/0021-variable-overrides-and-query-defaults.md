# 游戏与全局变量仅保存覆盖值，默认值由 Query 提供

游戏进度变量与跨存档变量具有不同生命周期，需要明确区分读写入口，同时避免 Model 访问同层 TablesModel。决定由两个 Model 共用普通 C# 覆盖值容器，以游戏／全局、整数／布尔四张独立表提供配置；Query 校验 ID 并将当前默认值传给 Model，读取不创建覆盖记录。全局 Model 完整负责自身文件加载、保存与脏标记，游戏变量随游戏存档捕获和恢复；变量持久化不校验配置 ID，业务 Query 和设置 Command 保留校验。

现行接口、通知与生命周期见[变量模块](../Architecture/Variables.md)，初始化时机见[初始化流程](../Architecture/Initialization.md)。

## 备选方案

- 初始化时把默认值写入 Model：需要额外初始化和重载流程，覆盖值与默认值难以区分，也会把配表默认值冻结进存档；选择在每次 Query 时组合默认值和覆盖值。
- 用 scope 参数统一游戏与全局入口：可以减少类型数量，但调用方需要运行时选择生命周期，强类型表引用与参数含义不够直接；选择独立 Command、Query、GM 和定义类型。
- 抽出全局加载／保存，再由外部确认保存成功并清脏：适合多个持久化策略，但当前只有一个独立文件，会增加快照交接、清脏和关闭保存协议；Model 通过 IStorageService 封装完整流程即可，不增加变量 System。
- 加载和保存时按最新配表过滤或拒绝 ID：可以清理废弃记录，但会让配置删除影响旧进度，且引入跨 Model 校验和回写流程；保留原记录，错误配置引用在业务入口暴露。

## 影响

- 未覆盖变量使用最新配置默认值；已经保存的覆盖值不随默认值变化。重置删除覆盖记录，设置成默认值不等同于重置。
- 相同有效值的设置不新增覆盖；底层覆盖记录变化仍按类型通知。批量清除和恢复先提交两个字典，再通知消费方，快照不共享可修改集合。
- 全局修改先在内存生效并通知，再显式原子保存；失败保留脏标记供同值操作或正常关闭重试。正常加载不标脏、不回写，文件读写不访问 TablesModel。
- 缺失变量数据时跳过恢复并保留当前状态；完整空快照仍表示清空覆盖。读取、解析或取消失败不提交临时加载结果。
- 废弃 ID 会继续保留；同表内复用 ID 可能重新启用旧值，需要保持身份稳定。旧存档格式的兼容或迁移由具体版本需求决定，不由配置 ID 校验代替。
