# 条件集中求值，消费方分帧轮询

条件种类增加时，集中观察需要同时维护求值、依赖收集和状态源监听，遗漏通知还会造成缓存与即时求值不一致。决定由 ConditionSystem 复用只读 ConditionContext 并提供即时求值，由消费系统通过既有调度器分帧检查自身对象、比较结果及响应变化，使新增条件只需实现求值。

轮询任务继续共用全局 SchedulerSystem 的时间片预算，由消费系统随 Procedure Attach/Detach 订阅和解除暂停及业务表重载通知，并通过 Token 暂停、恢复和取消。ProcedureContext 由所属 ProcedureSystem 构造注入，提供已生效暂停状态的只读视图；消费方不另维护活动布尔状态，以订阅、任务和登记版本表达生命周期。

本决定取代 [ADR-0010](0010-separate-condition-observation-and-action-dispatch.md) 的条件观察、缓存与通知部分，保留 ActionSystem 同步 FIFO 分发；同时取代 [ADR-0023](0023-explicit-condition-configuration-refresh.md)，删除观察缓存及 condition.refresh GM。当前接口与扩展约束见 [ConditionSystem](../Architecture/Conditions.md)。

## 备选方案

- 保留集中事件驱动：同 ID 共享缓存、状态变化后同步响应，但条件扩展持续增加状态源订阅与依赖收集维护。
- 集中维护通用轮询观察器：可以共享求值，但继续保留登记与通知生命周期；目前由消费方持有对象、采样结果和业务响应即可，不另建观察框架。
- 在 ProcedureContext 内另建时间片调度器：能自然随流程暂停，但会形成独立预算；选择保留全局预算，通过流程暂停通知控制任务，不新增流程调度队列。

## 影响

- 条件表达可采样的当前状态，不承担一次性事件捕获。接受两次采样之间的短暂变化被跳过，以及不同对象在不同时刻更新；一次性事实由业务事件或所属系统持久状态表达。
- 轮询复用现有时间片预算，不保证固定响应时间，也不保证单个生成或行为操作不会超出预算。无状态变化时仍会求值，相同条件可能被不同消费方重复求值。
- 暂停以流程实际生效状态为准，暂停期间重建的任务必须同步暂停；恢复沿用原游标。暂停通知只停止增量轮询，不阻止同步初始化和显式业务提交，也不替代流程退出时的取消与登记失效。
- 消费方必须区分求值和应用变化：NPC 配置不变时不重新定位，自动事件持续成立时不反复提交。事件提交前即时复核，只能阻止过期状态错误放行，不能消除 Collider 恢复的采样延迟。
- 后续求值直接使用重载后的配置；场景初始化仍同步完成，运行时由轮询推进，不维护全局条件快照或状态事务。
